
# Project Parasite — Technical Design

## 1. Technology Baseline

The project was initialized with:

- Angular CLI / Angular: 22.2.2
- TypeScript: 6.0.3
- Phaser: 4.2.1
- Vitest: 4.1.11
- Node.js: 24.19.0
- npm: 11.17.0

These versions were reported by the developer during initial environment verification. Inspect `package.json`, the lockfile, and installed packages before assuming they remain unchanged.

Do not upgrade dependencies merely because a newer version exists.

## 2. Application Model

SRP is initially a browser-based, offline, single-player application.

No backend, online multiplayer, cloud synchronization, or external account system is required by the initial scope.

Do not introduce these systems without an approved requirement.

## 3. Angular Responsibilities

Angular manages the application interface, including:

- Main menu and game entry flow.
- HUD and status presentation.
- Inventory and crafting interfaces.
- Settings and other application-level screens.
- Accessible controls and UI state.
- Coordination of application-level operations such as save/load requests.

Use modern standalone Angular components and supported Angular APIs.

Keep components focused on UI responsibilities. Avoid putting real-time gameplay calculations or large amounts of game-domain logic inside components.

## 4. Phaser Responsibilities

Phaser manages the active game experience, including:

- Game initialization and scene lifecycle.
- Rendering and animation.
- Player movement and game-world interaction.
- Collision handling.
- Gameplay input.
- World objects and entities.
- Real-time simulation and visual effects.

Follow APIs supported by the installed Phaser version. Do not copy Phaser 3 examples into Phaser 4 code without checking compatibility.

## 5. Angular–Phaser Integration

Establish a narrow, typed interface between the Angular application and the Phaser game.

The interface should support only the communication required by actual features, potentially including:

- Starting or stopping gameplay.
- Issuing gameplay commands.
- Receiving relevant gameplay events.
- Requesting presentation snapshots.
- Coordinating save/load operations.

These are candidate responsibilities, not a requirement to implement all of them immediately.

Avoid exposing Phaser internals directly to unrelated Angular components.

The game loop must not trigger unnecessary Angular change detection on every frame. Send presentation updates only when appropriate for the UI.

Ensure the game instance, input handlers, listeners, and other resources are cleaned up correctly when the owning component or scene is destroyed.

## 6. Gameplay Logic and State

Keep gameplay state under a clearly defined owner.

Use Phaser or an explicitly designed gameplay domain layer for active simulation state. Use Angular for presentation state.

Do not keep duplicate authoritative versions of the same gameplay value in both layers.

Prefer deterministic, independently testable rules for inventory, crafting, gathering, and survival calculations where practical.

Introduce additional domain modules only when they clarify responsibilities or make the implementation easier to test.

## 7. Project Structure

Follow the structure generated by the installed Angular CLI and the conventions established by the existing repository.

Organize code by responsibility. Add folders and files as actual features require them.

Do not create empty architectural layers for hypothetical future needs.

Keep application UI separate from gameplay simulation, and keep shared interfaces small and typed.

## 8. Assets and Rendering

Use Phaser's supported asset-loading and texture APIs.

Keep game assets organized and loading behavior explicit.

Do not assume that image paths, bundler behavior, or asset handling are identical between Angular templates and Phaser.

Use placeholder assets for early prototypes when appropriate. Record which assets are temporary and avoid misrepresenting placeholders as final artwork.

Prioritize clear rendering, predictable depth ordering, correct resizing, and stable performance before adding advanced visual effects.

## 9. Persistence

Persistence is planned but its exact implementation has not yet been finalized.

When implementing it:

- Define a versioned, typed save-data format.
- Validate saved data before restoration.
- Handle missing, corrupted, or incompatible saves.
- Handle browser storage failures gracefully.
- Avoid losing existing saves during schema changes.
- Keep serialization separate from UI and rendering logic.
- Prefer a storage abstraction when multiple systems depend on persistence.

IndexedDB is a candidate for structured local game saves. Confirm the requirements and implementation needs before committing to a storage design.

## 10. Testing

The initial project uses Vitest. Confirm the current test configuration before writing tests.

Use unit tests for deterministic rules and integration tests for important subsystem boundaries.

Use browser or manual gameplay checks when automated tests cannot establish that rendering, keyboard input, or gameplay behavior works correctly.

Do not assume that passing unit tests proves the game is playable.

## 11. Architecture Decision Process

Before introducing a major library, architecture, or cross-cutting abstraction:

1. Identify the problem it solves.
2. Inspect the current implementation.
3. Compare simpler alternatives.
4. Explain maintenance, performance, and testing implications.
5. Seek approval if the decision materially changes project scope or architecture.

Prefer incremental development and verified behavior over speculative complexity.
